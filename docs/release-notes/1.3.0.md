# dnsleaf 1.3.0 — pending release

This release prepares an explicit Windows DHCPv6 selection capability. Publication, production
enrollment and live Windows/PVE acceptance are separate operator work.

## Problem and behavior

Standard QGA provides address/prefix and interface identity, but not Windows DHCP provenance.
A synthetic same-interface inventory with DHCP /128, RA/Random /128 and RA/Link /64 reproduces the
reported limitation: the default selector refuses the two /128 candidates as ambiguous. The default
policy and its subprocess calls remain unchanged.

`selection_policy: windows-dhcpv6` opts a VM ipv6/both entry into one fixed, read-only PowerShell 5.1
metadata probe via synchronous `qm guest exec`. The strict IPv6 selector requires global usable QGA
addresses corroborated by MAC/address identity and consistent Windows provenance/state evidence:
Dhcp/Dhcp, Preferred and SkipAsSource=false. Exactly one eligible address is selected, regardless of
prefix-length ranking. No metadata or conflicting inventories cannot manufacture uniqueness.

`discover vm --selection-policy windows-dhcpv6 --family ipv6 --json` exposes raw discovery,
supplementary metadata, dispositions and selection separately. Both-family commands preserve each
family's result and fail overall when either cannot be selected. Metadata errors affect strict IPv6
without poisoning IPv4 or default-policy entries. Failed/ambiguous selection protects configured DNS
records from pruning. Plan/dry-run may query the Guest but never write DNS or Guest configuration.

## Implementation and compatibility

- A readable packaged script collects active IPv6 records and joins adapter identity by InterfaceIndex.
- Transport validates explicit completion, Guest exit status, non-truncation, schema and encoding;
  it uses the existing discovery timeout for the host and PVE wait, with no polling/retry framework.
- Pure correlation/selection is separate from acquisition. Raw and supplementary results are cached
  separately within one run only, including failures; default-only VMs perform no metadata query.
- Unknown policies and invalid source/family combinations fail before execution/planning. Entry edits
  keep full-document validation and atomic writes.
- Workspace schema 4, entries schema 2 and state schema 1 remain unchanged. Existing default entries
  need no YAML rewrite, workspace relocation, state migration or systemd reinstall when upgrading
  in the same Python environment. Opt-in requires Guest execution permission/capability separately.

## Validation and limits

Synthetic tests cover the reported before/after selection, DHCP /64, multiple adapters, incomplete or
conflicting evidence, enum/boolean validation, Unicode encoding, Guest execution errors and timeouts,
CLI/entry validation, per-family partial success, per-run reuse, and fake-provider apply/prune safety.
The entire suite and distribution/install/resource checks must pass under the documented Python
3.11/3.13 development workflow before release; see [release preparation](../release.md).

DHCP provenance is not a guarantee of permanent addressing or public reachability. Cross-query
inventories are not atomic and observed inconsistency causes refusal until a later ordinary run.
Host timeout does not prove termination of the Guest process. No Windows networking changes, VM
power changes, production entries or real DNS writes are performed by this implementation round.

The PowerShell 5.1 source and PVE transport contract were reviewed against official references;
the encoding/protocol tests use synthetic transport data. They do not establish live PowerShell
execution or real Windows/PVE/DNS acceptance. Retest even VMs whose old default selector found a
single /128, since that result did not establish DHCP provenance. See [discovery](../discovery.md).
