# dnsleaf 1.4.0 — pending release

1.4.0 intentionally removes the windows-dhcpv6 preset and accepts only the new source
configuration schemas. This is a breaking configuration release, despite retaining the requested
1.4.0 package version. It is not a backward-compatible package-only upgrade.

## Current model

- `workspace.yaml` requires explicit integer `config_version: 5`.
- `entries.yaml` requires explicit integer `config_version: 3` and an explicit entries list.
- Policies are `default` and `require-dhcpv6`; evidence sources are `none` and `windows-powershell`.
- Each dynamic strategy field independently resolves entry/discover CLI override, exact VM-ID
  source default, then package built-in (`default` / `none`). Null/omission inherits;
  explicit default/none overrides. Render/discover expose effective values and origins.
- Permission to acquire evidence is separate from demand: default never probes. Strict IPv6
  selection needs Windows evidence in this release; IPv4 retains its independent public selector.
- Static entries have no non-null policy/evidence overrides. Disabled entries must still validate.

The previous entry line `selection_policy: windows-dhcpv6` is replaced in a current-format file by:

```yaml
selection_policy: require-dhcpv6
evidence: windows-powershell
```

This example is documentation only. No preset, old-schema reader, automatic converter, migration
command, version dispatch or compatibility report is retained. Complete examples and exact
source-group restrictions are in [configuration](../configuration.md).

## Evidence boundaries and preserved safeguards

The existing fixed PowerShell 5.1 resource and PVE guest-exec transport are retained. Native Windows
origin/state data is owned by the adapter. A separate correlation step checks address/MAC/prefix
and full relevant inventory consistency before emitting generic facts. Strict selection is pure
and OS-independent: exactly one eligible global address with proven DHCP origin, preferred state
and skip-as-source=false. Unknown/conflicting evidence refuses selection; no /128 or EUI-64 fallback.
DHCP provenance does not establish permanent addressing or Internet reachability.

One raw source snapshot and at most one demanded supplementary acquisition per VM are shared only
within each run. Failed evidence does not poison default consumers or IPv4. Fresh runs query again.
Configured targets remain protected from prune; plan/dry-run performs no DNS mutations, though it
may acquire the fixed read-only evidence. Discovery neither enrolls entries nor checks publication.

Managed-record/last-apply state formats, credentials, workspace discovery, TTL/proxy behavior,
atomic writes and installed unit naming are unchanged. Preserve ownership history.

## Operator-controlled upgrade procedure

These are instructions for later deployment, not operations performed by this change:

1. Prepare current-format workspace and entries files separately, preserving the intended zone,
   token references, paths, TTL/proxy settings, unit names and entries. Use the reviewed 1.4.0
   package in an isolated environment to validate them. Do not place complete preparation copies
   directly among automatically searched sibling directories; use explicit paths.
2. Pause the scheduler under the operator's procedure and allow any current synchronization to
   finish. Coordinate package and both source-file replacements while scheduling remains paused.
   Keep a recoverable copy of the previous package/config pair. Do not purge or reset state.
3. Validate the installed package against the explicit existing workspace. Verify selection and
   inspect a dry-run plan before separately authorized DNS writes. Resume scheduling only after
   these checks. If reverting, restore the matching package/config pair while scheduling is paused.

No workspace relocation, token replacement or unit reinstall is required when the workspace and
installing interpreter paths remain unchanged. A package-only upgrade with old YAML will fail.
